码单器公共协作数据库 V1 完整实施方案
适用基线：码单器 8.2.25
方案版本：V1.0
整理日期：2026-07-18
推荐平台：GitHub + EdgeOne Makers
最终用户端交付：单文件 HTML
完整工程形态：用户端单文件 HTML + 管理员网页 + Edge/Cloud Functions + KV/Blob + 测试与文档

======================================================================
一、文件目的
======================================================================

本文件用于指导“码单器公共协作数据库”从方案、准备、开发、测试到发布的完整推进。

本方案已经吸收以下两份旧版长期维护指令中合理的工程纪律：
1.《工程推进指令 · 8.1长期维护版》
2.《获取方案指令 · 8.1长期维护版》

旧指令中的合理内容不原样堆叠，而是结合云端协作数据库的新风险进行适配。

本项目的真实目标不是做一个简单的公共网盘，而是建设一套：

“本地优先、匿名协作、按陪玩团与价格库隔离、普通变更自动匹配、敏感变更人工审核、可回滚、可导入导出、云端故障不影响本地码单”的公共数据协作系统。

======================================================================
二、对两份旧版指令的审视与吸收
======================================================================

（一）继续保留的合理原则

1. 文件与基线必须明确
- 当前稳定基线为码单器 8.2.25。
- 开发前保存原始文件、哈希和备份。
- 不凭文件名猜测目标版本。
- 多个旧版本并存时必须明确当前开发线和稳定线。

2. 稳定线与新功能线分开
- 8.2.25 继续作为稳定基线。
- 云端数据库属于新功能和新数据结构，不直接覆盖稳定版。
- 开发产物先进入候选线，完整验收后再晋升正式版。
- 发布阻断问题单独走热修线，不夹带新功能。

3. 最终用户端继续保持单文件 HTML
- 普通用户打开的码单器仍可保持单文件 HTML。
- 单文件内包含用户端 UI、业务逻辑和同步客户端。
- 服务器密钥、管理员密码、审核逻辑绝不能写进单文件。

4. 模块化源码优先于直接维护构建产物
- 若后续建立模块化工程，应修改源码并构建出单文件 HTML。
- 不应只修改部署后的 HTML，而不同步工程源码。
- GitHub 中的工程源码是开发权威；发布 HTML 是构建产物。

5. 数据保护优先
- 不随意修改原有 localStorage key。
- 不破坏现有备份、导入、导出结构。
- 云端字段必须通过白名单抽取，不能把本地对象整包上传。
- 任何迁移都要可回滚，禁止留下半成功状态。

6. 一轮只推进一个主项目
- 不同时实现身份、数据库、管理员后台、APK 后台同步等多个复杂项目。
- 每阶段完成后再进入下一阶段。
- 出现真实阻断时暂停原计划，先处理阻断点。

7. 使用“最小充分验证”
- 先做影响分析，再确定测试范围。
- 不因改动小就跳过最低完整性检查。
- 不因项目重要就每次机械执行全部测试。
- 数据、同步、导入导出、共享状态和权限属于高风险链路，应执行 L3 或 L4 验证。

8. 候选版完成后再晋升稳定基线
- 不直接覆盖稳定文件。
- 必须先通过数据兼容、离线、同步、权限、回滚和设备验证。
- 最终 HTML、GitHub 源码、部署产物和版本说明必须一致。

9. 区分三种“完成”
- 代码完成：功能已经实现。
- 自动测试完成：规定测试通过。
- 正式发布完成：部署、真实设备和回滚验证完成。
三者不能混为一谈。

（二）需要适配的新内容

1. “单文件”不再等于“整个工程只有一个文件”
完整工程还必须包含：
- 普通用户端单文件 HTML
- 独立管理员网页
- Edge Functions
- Cloud Functions
- KV 与 Blob 数据结构
- 数据 schema
- 自动测试
- 部署配置
- 回滚和迁移文档

2. 数据测试需要新增云端专项
除原有本地测试外，还需验证：
- 云端不可用时是否仍能本地码单
- 私人字段是否无法上传
- 两台设备一致提交是否能自动批准
- 冲突是否进入审核而不是覆盖
- 重复请求是否幂等
- 旧客户端是否会污染新数据
- 公共更新与本地修改冲突时是否保留本地值
- 审核发布后是否可回滚

3. 发布链路不再只是 GitHub Pages
需同时核对：
- GitHub 源码
- EdgeOne 预览环境
- EdgeOne 正式环境
- GitHub Pages 备用入口
- 管理员网页
- 云端 schema 版本
- 公共数据库版本

（三）不应继续机械执行的内容

1. 不应把所有云端逻辑塞进码单器单文件。
2. 不应把普通用户的整份本地数据库直接覆盖到云端。
3. 不应只根据库显示名称决定同步身份。
4. 不应把“每天同步”当成唯一同步方式。
5. 不应为了绝对实时而第一版引入 WebSocket。
6. 不应在尚未建立数据白名单前开放上传。
7. 不应在没有候选环境和回滚机制时直接接入正式用户。

======================================================================
三、已经确认的真实需求
======================================================================

1. 普通用户不需要注册账号。
2. 每台设备自动生成匿名 deviceId。
3. 用户可设置个人昵称；昵称允许重名。
4. 后台用“昵称 + deviceId 后四位”区分，例如“小鹿 #7C21”。
5. 管理员使用独立登录网页，不能使用普通匿名权限。
6. 价格库通过内置 groupId + libraryId 识别。
7. 文件名只用于首次辅助识别。
8. 用户即使改了库显示名称，也不影响同步。
9. 每个库可以选择：
   - 本地模式
   - 只接收更新
   - 参与协作
10. 首次绑定“参与协作”后，可以拆分提交全部允许共享的数据。
11. 两个不同设备提交相同内容，可自动批准。
12. 可信设备提交一次，可直接批准普通安全数据。
13. 有冲突的数据不自动覆盖，进入管理员审核。
14. 用户本地修改先立即保存，随后异步提交。
15. 正在使用的用户通过版本检查近实时收到更新。
16. 云端不能访问时，码单器继续离线正常使用。

四、最终平台组合
======================================================================

（一）GitHub

用途：
- 保存完整工程源码
- 保存稳定基线和候选分支
- 版本记录与回滚
- 保存 schema、测试、部署说明

（二）EdgeOne Makers

用途：
- 部署普通码单器网页
- 部署独立管理员网页
- Edge Functions：高频、轻量、低延迟接口
- Cloud Functions：复杂校验、匹配、审核、发布、导出
- KV：轻量状态、会话、版本提示、限流计数
- Blob：正式数据、提交记录、审核记录、事件和快照

（三）平台免费边界

截至 2026-07-18，EdgeOne Makers 官方免费版文档列出的主要额度包括：
- Edge Functions：每月 300 万次
- Cloud Functions：每月 100 万次
- KV：1GB
- Blob：1GB
- 项目总存储：5GB
- 构建：每月 500 次

这些额度远高于码单器 V1 的预计用量。

重要说明：
- 官方说明当前免费额度未来商业化后可能调整。
- 没有第三方平台能够保证永久、无条件、绝对免费。
- 本项目必须通过“本地优先 + 标准 JSON 导出 + 可迁移结构”避免被平台绑定。
- 如果未来免费政策改变，可以迁移到 Cloudflare D1、Supabase 或其他后端，而不重做用户端业务数据。

======================================================================
六、匿名身份设计
======================================================================

普通设备资料示例：

{
  "deviceId": "dev_01J...",
  "nickname": "小鹿",
  "nicknameTag": "7C21",
  "role": "normal",
  "createdAt": 1784352000000
}

规则：
- deviceId 首次打开时随机生成。
- 昵称可以不填，也允许重名。
- 昵称不是身份凭证。
- 服务器注册设备后签发设备令牌。
- 后续提交必须携带设备令牌。
- 令牌不得直接作为管理员凭据。

匿名身份的现实限制：
- 清理浏览器数据后会变成新设备。
- 换手机不能自动恢复身份。
- 一个人理论上可以制造多个匿名设备。
- “两设备确认”主要防止误操作，不是强实名防作弊机制。

防护方式：
- 单设备限流
- 异常提交检测
- 可信设备白名单
- 管理员封禁
- 敏感数据人工审核
- 所有批准均保留审计记录

======================================================================
七、陪玩团与价格库身份
======================================================================

每个团和库必须有稳定身份证：

{
  "groupId": "group_xiacijian",
  "groupName": "下次见",
  "libraryId": "lib_xiacijian_regular",
  "libraryName": "下次见常驻价格表",
  "schemaVersion": 1
}

识别优先级：
1. 文件内部 groupId + libraryId
2. 已登记文件名和别名
3. 用户手动确认

文件名示例：
- 下次见常驻价格表
- 下次见赛季初价格表

文件名只作为辅助识别，真正绑定的是 libraryId。

每个库独立保存绑定模式：
- local：仅本地
- receive：只接收
- collaborate：接收并参与协作

======================================================================
八、首次绑定与首次共享
======================================================================

用户选择“参与协作”后：

1. 先执行私人字段过滤。
2. 将可共享内容拆成单条候选。
3. 逐条与公共库比较。
4. 不使用整库覆盖。

逐条处理规则：
- 公共库已有相同内容：忽略。
- 公共库没有，只有一个设备提交：等待第二份确认。
- 两个不同设备提交相同内容：自动批准。
- 可信设备提交普通安全内容：一次批准。
- 同一业务键出现不同内容：进入审核。
- 敏感规则：直接进入审核。

======================================================================
九、数据共享边界
======================================================================

（一）自动共享或自动候选

1. 普通单价
2. 服务类型名称
3. 已确认陪玩名字
4. 新老板资料
5. 已有老板折数降低

（二）必须审核

1. 区间规则
2. 加价规则
3. 礼物规则
4. 老板直属变化
5. 老板折数升高
6. 删除价格
7. 删除老板
8. 整库导入覆盖
9. 库重命名或重新绑定
10. 价格冲突
11. 同名老板冲突
12. 异常大幅价格变化
13. 异常大幅折数下降

（三）永不上传

1. 历史记录
2. 订单内容
3. 原始聊天
4. 备注
5. 最近老板使用记录
6. 锁定字段
7. DIY 布局
8. 布局模板
9. 自定义比例
10. 使用次数
11. 最近使用时间
12. 用户个人排序和临时状态
13. 原始名字修正上下文

服务器也必须使用字段白名单，不仅依赖前端自觉过滤。

======================================================================
十、普通价格规则
======================================================================

价格业务键：

groupId
+ libraryId
+ normalizedServiceName
+ settleType
+ ruleType
+ variant

新增普通价格自动批准条件：
- 两个不同 deviceId
- 同一个 groupId
- 同一个 libraryId
- 服务名称标准化后相同
- 结算方式相同
- 单价相同
- 没有正式项目或冲突候选

可信设备提交一次可批准。

修改已有价格自动批准条件：
- 两个不同设备提交相同新值
- 涨跌幅不超过 ±10%
- 项目业务键相同
- 没有其他冲突值

否则进入人工审核。

服务类型跟随价格项目共享，不单独建立重复数据库。

======================================================================
十一、陪玩名字规则
======================================================================

陪玩名字业务键：
groupId + normalizedName

自动批准条件：
- 两个不同设备确认同一个名字
- 或可信设备提交一次
- 名字长度合法
- 经过 Unicode NFKC 规范化
- 清理首尾和重复空格
- 不含链接、联系方式、控制字符和异常长内容

只上传最终确认名字，不上传：
- 原始聊天
- 名字出现在哪一笔订单
- 修改前错误名字
- 用户历史提取内容

======================================================================
十二、老板信息规则
======================================================================

公共老板字段：

{
  "bossId": "boss_xiacijian_0001",
  "bossName": "小鱼",
  "paiDan": "小雪",
  "discount": 0.97
}

说明：
- 派单与直属为同一字段。
- 新数据优先使用 bossId。
- 旧数据无 bossId 时，可临时按 groupId + normalizedBossName 匹配。
- 同名冲突时不得自动猜测。

新老板自动批准条件：
- 两个不同设备提交相同的老板名、直属和折数
- 或可信设备提交一次
- 折数在 0.8～1 范围内

公共库新增老板后：
- 同团用户本地没有该老板，也允许通过同步自动新增。

已有老板折数下降：
例如 0.98 → 0.97。

自动批准条件：
- 折数范围为 0.8～1
- 两个不同设备提交同一个新折数
- 直属没有变化
- 没有其他冲突折数

必须审核：
- 折数升高
- 直属变化
- 删除老板
- 折数超出 0.8～1
- 同名老板匹配不明确
- 多个冲突折数
- 异常大幅下降

十三、自定义比例
======================================================================

自定义比例完全保留本地，不参与公共共享。

包括：
- 单子比例
- 礼物比例
- 用户自建比例卡
- 当前选择的比例
- 临时比例变化

======================================================================
十四、提交与自动审核流程
======================================================================

用户修改：
1. 立即写入 localStorage。
2. UI 立即使用本地结果。
3. 停止操作 5～10 秒后生成原子变更。
4. 上传失败则进入本地 pendingCloudChanges 队列。
5. 网络恢复后自动重试。

服务器收到提交：
1. 验证设备令牌。
2. 验证 groupId 和 libraryId。
3. 验证请求大小。
4. 按字段白名单清洗。
5. 标准化名称和数字。
6. 重新生成业务键和内容 Hash。
7. 与正式数据比较。
8. 与其他候选提交匹配。
9. 执行该类型安全边界。
10. 输出状态。

状态：
- waiting_confirmation
- auto_approved
- pending_review
- approved_by_admin
- rejected
- superseded

两设备确认必须满足：
- deviceId 不同
- 设备令牌不同
- 标准化内容 Hash 相同
- 提交都有效且未撤销
- 没有触发异常限流

======================================================================
十五、同步频率
======================================================================

用户端启动：
- 立即读取本地数据。
- 立即显示码单器。
- 后台发起版本检查。
- 服务器失败不阻塞启动。

页面在前台：
- 默认每 60 秒检查版本。
- 长时间无变化可降到每 120 秒。
- 页面切到后台时暂停。
- 回到前台时立即检查。
- 网络恢复时立即检查。
- 用户刚提交后可额外检查一次。

管理员网页：
- 打开时立即检查。
- 前台每 15 秒刷新待审核数量。
- 页面重新获得焦点时立即检查。
- 第一版不使用 WebSocket。

KV 具有最多约 60 秒边缘缓存延迟，因此它适合版本提示、会话和限流。
正式数据、提交、审核和快照放 Blob。
需要立即读取最新值时使用 Blob 强一致读取。

二十、安全与隐私
======================================================================

1. 管理员密码不写进 GitHub。
2. 管理员密码、JWT 密钥放在 EdgeOne 环境变量。
3. 管理接口必须鉴权。
4. 登录失败需要限流。
5. 关键写入需要防重复和幂等。
6. 提交接口限制请求大小。
7. 每台设备设置分钟和小时提交上限。
8. 服务器按白名单接收字段。
9. 所有正式发布都有来源、时间、版本和回滚记录。
10. 不记录订单内容与原始聊天。
11. 不公开完整 deviceId，只显示缩短标记。
12. 不把平台 API Token 放入普通用户端。

建议限制：
- 单设备每分钟最多 5 次提交
- 单设备每小时最多 50 次提交
- 单次提交最大 64KB
- 昵称最多 20 字
- 服务名称最多 50 字
- 老板名称最多 30 字

======================================================================
二十一、冲突与合并
======================================================================

公共新增，本地没有：
- 自动添加。

公共数据与本地完全相同：
- 只更新公共元数据。

公共更新，本地仍是旧公共版本：
- 自动更新。

公共更新，但本地已经自行修改：
- 不静默覆盖。
- 保留本地值。
- 记录公共新值。
- 标记冲突。

本地待审核项目：
- 继续本地使用。
- 批准后标记为公共。
- 拒绝后用户可保留为本地项目或恢复公共值。

二十七、V1 验收标准
======================================================================

1. 网页打开时不等待服务器。
2. 断网仍能正常码单。
3. 云端失败不损坏本地数据。
4. 私人字段无法通过接口上传。
5. 两个设备提交相同普通新增能够自动批准。
6. 冲突不会自动覆盖。
7. 老板折数只在 0.8～1 内按规则下降。
8. 直属变化进入审核。
9. 用户本地没有的公共老板可以新增。
10. 自定义比例永不上云。
11. 管理员能批准、拒绝、修改后批准和回滚。
12. 重复请求不产生重复记录。
13. 每个批准事件可追溯。
14. 每个公共库可完整导出。
15. GitHub Pages 备用入口仍可本地使用。
16. Android、iPhone、iPad/平板和桌面适用链路完成验证。
17. 最终用户端仍输出单文件 HTML。
18. GitHub 源码、构建产物、部署版本和说明一致。

- 建议计算 SHA-256 哈希并保留副本。

2. GitHub 仓库

- 确认自己拥有仓库管理权限。

- 正式 main 分支暂不接入实验后端。

3. EdgeOne Makers 账号
- 注册或登录。
- 暂时只创建测试项目。
- 连接 GitHub 开发分支。
- 第一阶段使用平台默认域名，无需购买域名。

4. 首批公共库
建议先只选择一个陪玩团和两个库：
- 下次见常驻价格表
- 下次见赛季初价格表

准备每个库的脱敏导出文件。
不要包含历史、备注、布局和个人比例。

5. 身份表
为首批库确定：
- groupId
- libraryId

建议：
groupId：group_xiacijian

赛季初库：lib_xiacijian_season_start

6. 测试设备
至少准备：
- 两个不同浏览器或设备，用于两设备确认
- 一台 Android 或 APK 环境
- 一台 iPhone/Safari
- 一台 iPad 或平板环境（可以后期实测）

7. 管理员资料
- 准备管理员登录邮箱或用户名。

8. 初始可信设备
- 确定是否把你自己的设备设为 trusted。
- 建议第一批只设一台可信设备。
- 其他设备先作为普通匿名设备测试。

9. 试运行范围
- 第一阶段不要直接开放给所有用户。
- 建议先找 2～5 个测试用户。
- 只测试一个团和两个价格库。
- 连续观察至少一轮真实新增、冲突、审核和回滚。

三十一、最终决定
======================================================================

主平台组合确定为：

GitHub
+
EdgeOne Makers Pages
+
Edge Functions
+
Cloud Functions
+
KV
+
Blob

设计取向：
- 普通码单器仍是单文件 HTML。
- 完整云端工程采用模块化源码。
- 本地数据永远是可用底座。
- 公共数据通过事件、审核和版本发布。
- 普通用户不直接覆盖公共库。
- 私人数据从客户端和服务器两侧共同阻断。
- 先建立边界和 schema，再接入真实网络。
- 先小范围试运行，再晋升稳定版。
- 所有公共数据可导出，平台改变时可迁移。

本方案是 V1 开发基线。后续每次修改方案，应更新版本号、日期、变更原因和影响范围。
